## Findings

Four findings: one High and three Medium. No Critical finding was supported. Static findings identify code paths; their stated runtime limitations are not claims of an exploited production system.

### SEC-001 — Deployment exposes the database password in a process argument
- Severity: High
- Confidence: static evidence
- Location: `deploy/deploy.sh:91`; `deploy/provision.sh:83`; `deploy/provision.sh:99`; `docs/deployment.md:67`
- Requirement: ADR 0009, dedicated site user/database isolation on the shared VPS; `deploy/CLAUDE.md`, secrets stay in `shared/.env`; provisioning explicitly avoids secret-bearing argv because other server users can read arguments.
- Evidence: provisioning writes a password-bearing PostgreSQL URI to `DATABASE_URL`. Deployment sources that environment and passes the entire URI as the final `pg_dump` argument when taking its pre-migration snapshot. The documented manual `pg_restore -d` command also expands the full URI into argv. This exposure is present regardless of correct shell quoting. The daily backup script uses the database name under the postgres user and does not have this same argv issue. No real credential was read or printed during the audit.
- Impact: while the command runs, another unprivileged site process can obtain Vertex Hub's database credential if cross-user process arguments are visible, undermining the dedicated database isolation and enabling database reads/writes. Cross-user `/proc` visibility and database reachability on production were not probed; no repository provision rule establishes a mitigation for argument visibility.
- Suggested fix: use a protected libpq password file/service configuration and a credential-free database target for both snapshot and documented restore commands. Keep any temporary credential file private, and remove it on exit.
- Verification: run the changed commands with fake credentials in an isolated Linux environment; inspect argv as another unprivileged user and confirm no password appears, then confirm snapshot and restore still authenticate. Separately confirm the host's process-visibility controls in an explicitly approved server session.

### SEC-002 — Post-login destination validation accepts externally normalized URLs
- Severity: Medium
- Confidence: static evidence
- Location: `apps/web/src/lib/auth.ts:71`; `apps/web/src/routes/login.tsx:17`; `apps/web/src/routes/login.tsx:20`; `apps/web/src/routes/login.tsx:42`; `apps/web/src/lib/safe-redirect.test.ts:12`
- Requirement: `safeRedirect` promises same-origin post-login paths; authentication must not send a user to an attacker-controlled destination through a user-supplied login query.
- Evidence: evaluating the actual authored function body in Node accepts `/\n/attacker.invalid`, `/\t/attacker.invalid` and `/\r/attacker.invalid`. Resolving each returned value with `new URL(value, 'https://hub.vertexmedia.pro')` produces `https://attacker.invalid/`. The login route forwards this value to both `redirect({ href })` and `router.navigate({ href })`; its query validation does not remove controls. Existing tests reject `//host` and `/\\host` but omit ASCII control characters. TanStack's [NavigateOptionsType](https://tanstack.com/router/latest/docs/api/router/NavigateOptionsType) and [redirect function](https://tanstack.com/router/latest/docs/api/router/redirectFunction) document external navigation through `href`. An installed-version browser navigation was not executed.
- Impact: a crafted login link can pass the application's redirect validator and potentially navigate a signed-in user to an external page after authentication, enabling phishing through an otherwise trusted entry URL. This is not evidence that cookies or credentials are sent to that destination.
- Suggested fix: reject control characters, resolve the candidate against the app origin, require the resolved origin to match and return the validated local path/search/hash. Keep ordinary local redirect targets working.
- Verification: extend the redirect regression cases to tab/newline/carriage-return inputs and their encoded query forms; confirm external targets resolve to the fallback, then verify both already-signed-in and post-sign-in navigation with a stubbed browser destination.

### SEC-003 — Template links disclose metadata of an archived client's retainer
- Severity: Medium
- Confidence: static evidence
- Location: `apps/api/src/modules/templates/templates.service.ts:609`; `apps/api/src/modules/templates/templates.service.ts:192`; `apps/api/src/modules/templates/templates.service.ts:143`; `apps/api/src/modules/projects/engagement-directory.ts:185`; `apps/api/src/modules/clients/client-directory.ts:50`; `apps/api/src/modules/projects/retainer-access.ts:61`
- Requirement: F05, rule G2 and API access rules: archiving a client hides its projects and retainers; callers without `projects.manage` scope `all` cannot read that archived work. ADR 0013, services must not return records outside the caller's scope.
- Evidence: an employee may read a live template. `linkedRetainers()` loads linked retainers through `EngagementDirectory.retainers()` and excludes only the retainer's own archive flag. That directory returns no client archive state. Template detail then loads client summaries without an archive filter and emits the linked retainer id/name and client id/name. The template list counts these links too. Archiving a client leaves its retainer and template link intact (`ClientsService.archive` only changes the client archive flag), while direct retainer detail correctly refuses that employee through `retainer-access.ts:61`.
- Impact: when a live template links a non-archived retainer whose client was archived, an ordinary employee can still see the archived client's name and retainer identity through template detail, and its existence through link counts. No money fields or full retainer detail are exposed by this path.
- Suggested fix: apply the parent-client archive visibility rule when assembling linked-retainer metadata and counts, using the caller's access. Preserve the module boundary by exposing the required directory filter or access-aware summaries.
- Verification: link a monthly template to a retainer, archive its client in a dedicated test fixture, and assert an employee's template detail/list omit the hidden link/count while direct retainer access remains 404; test restoration and authorized manager behavior as well.

### SEC-004 — Initial task creation stores attachment share tokens in the audit log
- Severity: Medium
- Confidence: static evidence
- Location: `apps/api/src/modules/tasks/tasks.service.ts:422`; `apps/api/src/modules/tasks/task-parts.service.ts:169`; `apps/api/src/modules/audit/record-audit.ts:37`; `apps/api/test/task-parts.test.ts:214`
- Requirement: F06, "Audit, notifications and jobs" (`docs/specs/F06-tasks.md:272`): link audit data keeps label and host only, never the full URL because it may contain a share token; API audit rules prohibit tokens in audit entries.
- Evidence: `TasksService.create` copies `input.links` directly into the `task.created` audit entry's `after.links`. `recordAudit` inserts this object without redaction. A URL such as the fake fixture `https://drive.example.com/file/abc?token=secret` therefore persists its token in audit JSON when supplied during initial task creation. Adding a link later correctly writes only `{ label, site }`; the existing dedicated-link test explicitly asserts the audit does not contain `secret`, but initial creation lacks that protection.
- Impact: attachment access tokens supplied with a new task are duplicated into the indefinitely retained audit log. Removing/archiving the task link does not remove that copy, extending token retention and making it visible through audit/export/backup access.
- Suggested fix: map initial links to the same label/host audit shape used by `TaskPartsService.addLink`. Assess existing audit rows for token-bearing URLs through an explicitly authorized remediation process.
- Verification: create a task with a fake token in an initial attachment's path/query/fragment; assert the task retains its usable URL while `task.created` audit JSON contains only the allowed label/host and no token. Keep the dedicated add/remove-link regression.

## Limitations and unverified items

- SEC-001's argv behavior is definite, but production process visibility and network/database access were not inspected; this audit has no authorization to access the server. The runbook/provision source is the evidence available here. Shared nginx `security-headers.conf`, global general/per-IP zones, fail2ban behavior, TLS certificates and effective server permissions are outside the checkout and unverified.
- SEC-002's validator failure and URL normalization are confirmed locally. Actual router handling of those values in the installed browser build remains unverified; no external destination was visited. Router source was not found at the initially guessed dependency path. The coordinator supplied the primary TanStack documentation links above.
- **Public redemption abuse follow-up:** `user-links.service.ts:66` hashes a supplied password before querying/rejecting the token. This endpoint is anonymous, outside Better Auth's `/api/auth` limiter, and has no dedicated nginx limit in the authored site. The general host zone may bound it, but its definition is external. Invalid-token traffic can therefore request unnecessary password-hashing work; practical load, memory cost and pilot impact were not measured. Rejecting invalid links before expensive hashing and adding a focused limiter should be evaluated in a later authorized test. No denial-of-service finding is asserted without that evidence.
- No vulnerability/advisory scan or dependency resolution inspection was performed; lockfiles/generated output were excluded as required. Better Auth defaults (cookie/CSRF/backup-code implementation and endpoint internals) were not independently runtime-tested. Declared auth configuration and authored negative tests do not establish a complete library security assessment.
- Race tests, multi-role live negative checks, immediate access revocation, 2FA backup-code reuse, rollback behavior and live nginx rate limits remain unexecuted. Static inspection does not certify these behaviors.
- Q4 off-server backup destination is explicitly unresolved in `docs/open-questions.md:7`; the local backup script itself says off-server copies are required before launch. This is an owner-controlled launch dependency, not a newly discovered code defect. Q5 email and later-phase files/client approvals remain outside this deploy audit's missing-feature scope.

## Deploy implications

SEC-001 warrants resolving secret-bearing argv before the Phase 1 deploy, or explicit owner acceptance supported by verified host mitigations. The three Medium findings need a pilot decision and focused fixes/tests; this audit makes no remediation. Complete the unverified live access/security checks and the owner's backup decision before treating these reports as production-readiness evidence. The lack of a supported Critical finding is not a certification of security.
