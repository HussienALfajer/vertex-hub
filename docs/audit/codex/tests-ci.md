## Findings

### CI-001 — A failed PM2 release switch exits before automatic rollback
- Severity: Medium
- Confidence: static evidence
- Location: `deploy/deploy.sh:45`; additional locations: `deploy/deploy.sh:10`, `deploy/deploy.sh:43`, `deploy/deploy.sh:96`, `deploy/deploy.sh:100`, `deploy/deploy.sh:102`.
- Requirement: `deploy/CLAUDE.md`, rollback requirement; `docs/deployment.md:47`, an unhealthy release restores the previous release; `deploy/deploy.sh:9`, the script's stated recovery behavior.
- Evidence: `switch_to` first replaces `current`, then calls `pm2 startOrReload` and `pm2 save` as unguarded commands. The top-level deploy calls this function as an ordinary command under `set -euo pipefail`, after removing the `ERR` trap. If either PM2 command returns nonzero, Bash exits before reaching `if ! healthy` and its restoration branch. The symlink already references the new release. No CI job or authored test exercises this failure path. This is a trace of shell control flow; no PM2/deploy command was executed.
- Impact: a reload failure can leave the deployment pointing at a partially started or unavailable release without the advertised automatic recovery. A failed `pm2 save` can also leave a switched release whose persisted process state was not saved, even if processes happened to start successfully. Recovery requires owner intervention rather than the existing fallback branch.
- Suggested fix: explicitly check the PM2 command results during the switch and route a failed switch through restoration of the captured previous release. Account for Bash's changed `errexit` behavior when a function is used in a conditional: test each command rather than assuming `set -e` will stop inside it. Preserve the failed command/recovery diagnostics and return a failure status.
- Verification: in a disposable local script harness with mocked `pm2`, filesystem commands and health probes, fail `startOrReload`, then fail `save`; each run must attempt to restore the previous release and exit nonzero. Also cover a successful switch, health-probe failure, first deployment with no predecessor, and recovery failure. Run syntax checks before a later owner-approved deployment drill.

No additional independently counted test/CI defect is asserted. Missing coverage for defects reported in another area is retained below as regression work, not counted again under a new severity.

### Authorization, atomicity, races and isolation

- API suites contain broad 401 and wrong-role/wrong-client/wrong-department/wrong-assignee assertions. `tasks.test.ts:61` also covers anonymous dependency writes, even though those cases are absent from the dedicated dependency file. Negative coverage must be traced across files, not inferred from a single test filename. Read-all grants and session-only personal endpoints do not inherently have a valid 403 case; notification ownership correctly expects 404 (`notifications.test.ts:175`). Runtime access metadata checks ensure a declaration exists, not that the declared grant or every service scope is correct.
- Rollback primitives are exercised in `audit.test.ts:106` and `notifications.test.ts:329`: each writes through a transaction, throws, and asserts no stored entry. These do not prove every business controller/service uses the same transaction, nor do they inject a late failure into every composite template/task/cycle mutation. Normal-flow audit-shape assertions supply complementary evidence, not a universal atomicity guarantee.
- `task-status.test.ts:229` issues two status changes with `Promise.all` and expects 200/409. `task-dependencies.test.ts:199` parallelizes creation of eleven independent tasks to test the limit; it does **not** concurrently edit graph edges. Cycle/template/reminder/heartbeat suites mostly demonstrate sequential repeat-run idempotency, not simultaneous attempts or mid-transaction races.
- API files are serialized (`apps/api/vitest.config.ts:17`), while root Turbo may run package suites together. DB migration callers are explicitly serialized with a shared session advisory lock (`packages/db/src/migrate.ts:8`–`27`); a simultaneous-boot migration race is therefore not asserted merely from multiple global setups. API tests disable jobs, use random emails/IDs/run-scoped searches, and clean dependent records through shared helpers/casts. Global department manager rows explain the API's deliberate file serialization.
- The test DB remains shared rather than isolated per run. `users.test.ts:489` explicitly expects its seeded GM to be the only active GM; department suites alter global seeded departments and restore/clear them. Review/execute these tests only against a dedicated disposable test database, never a development database with owner records, and avoid independent concurrent API-suite invocations against the same database. Failure during seeding/cleanup and repeated/shuffled execution were not tested here.

### CI, scripts and release reproducibility

- `.github/workflows/ci.yml` defines three jobs: checks with PostgreSQL 17; Chromium Playwright; full-history Gitleaks. Installs use frozen lockfiles and Node from `.node-version`; workflow permissions are read-only and superseded runs are cancelled. Checks run lint, typecheck, tests and build, then regenerate/check authored-schema migration output and web OpenAPI/client output for drift. Migration drift also checks untracked files. The browser job uploads reports and test results even on failure.
- Root scripts use Turbo; both `typecheck` and `test` depend on upstream builds (`turbo.json`). Running the default commands would emit artifacts even for an otherwise pure suite. Direct no-emit compiler and isolated Vitest invocations were therefore used here. Package exports resolve built contracts/DB types, so successful direct checks rely on the existing installed/build dependency state and do not prove a clean checkout can install/build successfully.
- `package.json` declares pnpm 12.4.1 and Node >=24; `.node-version` selects 24 for CI. Shared TS configuration enables strict, unchecked-index, override/fallthrough and unused-code checks. `pnpm-workspace.yaml` declares a 24-hour release-age guard and a limited install-script allowlist. Lockfiles/resolution data were deliberately not read, so dependency resolution and a fresh install were not certified.
- `deploy/deploy.sh` resolves a commit, archives it into a timestamp/SHA release, installs with the frozen lockfile, builds, takes a pre-migration snapshot, migrates, switches `current`, reloads PM2, polls API health and prunes releases. A deploy lock prevents concurrent deployments. Rollback switches code without reverting migrations; compatibility and a tested backup restore remain essential. `deploy/bin/vertexhub-deploy` supplies a clean environment and the latest script from `origin/main`, even when deploying another ref. These paths were traced only; the host's Node/Corepack/PM2/Postgres/nginx versions and permissions were not inspected.
- Release readiness polls API/database health only (`deploy/deploy.sh:34`, `apps/api/src/modules/health/health.service.ts:11`). The periodic host check separately inspects PM2 state for API and worker. Neither observed CI execution nor a worker-failure/queue-liveness deploy drill is available in this audit. CI has no shell-syntax, mocked release-failure, backup-restore or nginx-configuration job. Those are coverage limitations rather than additional defects claimed here.
